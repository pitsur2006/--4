# КТ3_1 — Redis Cluster

**Работа: Пицур АП.** [Условие задания](screenshots/00_условие_КТ3_1.png).

## Пункт 1. Развёртывание кластера

Сценарий `failover.py` запускает девять узлов Redis на портах **5500–5508**: три мастера и шесть реплик, по две на каждый мастер. `redis-cli --cluster create --cluster-replicas 2` распределяет между мастерами все 16 384 слота. Сценарий проверяет состав кластера и состояние `cluster_state:ok`.

Девять узлов моделируются девятью процессами на одном Linux-хосте. Это воспроизводит вариант с портами 5500–5508 из задания; девять отдельных физических компьютеров не используются.

## Пункт 2. Сбой и восстановление

Сценарий записывает `f=888`, ждёт подтверждения двух реплик, останавливает мастер `5500` сигналом `SIGSTOP` и проверяет, что его реплика автоматически получает слоты `0–5460`. Затем проверяются `cluster_state:ok` и чтение `f=888`. После `SIGCONT` прежний мастер должен вернуться в роли реплики.

Запуск на Linux с установленными `redis-server` и `redis-cli`:

```bash
python3 KT3_Redis/failover.py
```

Автоматическая проверка и снимки настоящего терминального окна выполняются в [GitHub Actions](../.github/workflows/kt3_redis_failover.yml). Отчёт DOCX со ссылкой на запуск и скриншотами находится в этой папке.

Redis Cluster использует асинхронную репликацию. `WAIT 2 5000` уменьшает риск потери проверочной записи, но не гарантирует строгую согласованность: [документация Redis](https://redis.io/docs/latest/management/scaling/).
